CS 121 Search Engine

Milestone 3 Report

System Overview

This project implements a search engine for the full ICS developer corpus without using a text-indexing library. The system consists of two programs: indexer.py, which builds a disk-based inverted index, and searcher.py, which accepts console queries and returns ranked URLs.

Milestone 3 uses ranked retrieval rather than Boolean AND retrieval. Documents containing any available query term are considered, and their TF-IDF contributions are accumulated. Documents are not excluded merely because they do not contain every query term.

Indexer Design

Document Processing

  • Reads each page's url and content from JSON.
  • Removes URL fragments before storing URLs.
  • Uses BeautifulSoup to handle normal and broken HTML.
  • Excludes script, style, and noscript content.
  • Uses a lighter extraction path for plain text and unusually large HTML files.

Tokens and Important Words

Tokens are all alphanumeric sequences matched by [A-Za-z0-9]+. They are lowercased and Porter stemmed. Stop words and numeric tokens are retained.

Text in title, h1, h2, h3, b, and strong tags is counted separately as important text. Each posting stores the document ID, normal term frequency, and important-term frequency.

Partial Indexes

The indexer flushes its in-memory inverted index to a sorted partial index every 5,000 documents. This exceeds the requirement to offload at least three times. A k-way heap merge combines the partial indexes into index.txt. During the merge, the indexer also builds index_seek.json, which maps each token to its byte offset.

Search and Ranking

The searcher loads the seek table and URL map, but it does not load the complete inverted index into memory. It seeks directly to each query term's postings in index.txt.

Candidate documents are the union of documents containing any query term. TF-IDF contributions are accumulated across all matching terms:

score(t, d) = (1 + log(tf + 5 × important_tf)) × (log((N + 1) / (df + 1)) + 1)

Additional ranking components include:

  • A coverage multiplier that favors documents matching more query terms.
  • Bonuses when query terms appear in the URL.
  • Penalties for raw data files and dataset paths.
  • URL normalization to remove equivalent results such as / and /index.html.

Operational Requirements

  • The inverted index is stored in filesystem files rather than a database.
  • The indexer repeatedly offloads partial indexes and merges them.
  • The searcher reads postings from disk using byte offsets.
  • The console interface returns ranked pages identified by URL.
  • No Lucene, PyLucene, ElasticSearch, or similar indexing library is used.
